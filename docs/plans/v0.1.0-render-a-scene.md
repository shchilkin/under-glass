# v0.1.0 — Render a Scene

`v0.1.0` proves that Under Glass can load a portable, host-owned scene and present it as deterministic true 3D. It ends with a tagged GitHub release and public playground preview, but does not publish npm packages.

## Release contract

- The repository and every `@under-glass/*` workspace package use the lockstep version `0.1.0` at release time.
- One canonical, immutable Visualization JSON fixture drives the playground and browser evidence.
- The renderer accepts one snapshot, reaches a stable lifecycle state, switches between the two canonical camera modes, and is recreated for a different Visualization.
- Every feature lands through its own pull request into `development`; agents do not merge those pull requests, and squash merge is the only permitted merge method.
- Issue #10 establishes the CI foundation before feature implementation starts. Pull requests into `development` are protected by separate required project-check and Fallow jobs. The project check runs the repository's install and `npm run check` contract on Node 24; Fallow runs a blocking `audit` with a `new-only` gate and inline annotations so a pull request cannot introduce new structural quality findings.
- CI runs for every pull request into `development`, cancels an older in-progress run when the same pull request receives a new commit, and repeats the project check after changes reach `development`. Fallow's `new-only` comparison remains pull-request scoped. Scheduled and nightly workflows are outside the v0.1 contract.
- A separate required browser job exists from the CI foundation onward. It runs the playground smoke test in the official Playwright Noble container pinned to the repository's exact `@playwright/test` version, using the browsers and system dependencies already baked into that image rather than installing browsers during the workflow. Browser behaviour coverage grows with each renderer slice; issue #7 adds the canonical screenshot baselines and teardown gates.
- A failed browser job retains its Playwright report, traces, and screenshot diffs for seven days. Successful browser runs upload no artifacts.
- Pull-request workflows use the `pull_request` event with a read-only token, receive no repository secrets, and never use self-hosted runners. They do not use `pull_request_target`; Fallow remains a blocking analysis even when GitHub cannot publish richer annotations for a fork contribution.
- v0.1 has no repository-wide code-coverage percentage threshold. Required unit, browser, visual, and teardown tests prove the named release invariants directly, and no required job may be weakened with `continue-on-error`.
- Branch protection accepts required checks only from a feature branch that includes the current `development` head. Updating a stale branch reruns every required check before squash merge; v0.1 does not use a merge queue.
- Every external GitHub Action, including actions published by GitHub, is pinned to a verified full commit SHA. A nearby comment records the corresponding human-readable release version.
- Dependabot checks GitHub Actions weekly and groups their immutable-reference updates into one pull request. Automated npm dependency updates are outside the v0.1 CI policy.
- Required jobs use no path filters: project check, Fallow, and browser verification always report an explicit status for every pull request, including documentation-only changes.
- Browser tests receive one retry in CI solely to collect retry-time traces, while local runs receive none. Playwright's flaky-test failure mode remains enabled, so a test that passes only on retry still fails the required browser check.
- Browser tests run with one worker and no sharding in v0.1 to keep WebGL and screenshot execution deterministic. Parallelization is reconsidered only after the stable suite approaches ten minutes.
- Required jobs have explicit timeouts: ten minutes for the project check, five minutes for Fallow, and fifteen minutes for browser verification. A timeout fails the check; the workflow never retries an entire job automatically.
- CI caches only npm's download cache, keyed by the lockfile. Every job still performs a clean `npm ci`; `node_modules`, build output, and Playwright browsers are never restored from workflow caches.
- The `development` ruleset has no administrator bypass. Emergency changes use the same pull-request, required-check, current-branch, and squash-merge path as every other change.

## Persisted contracts

The existing Visualization v1 contract remains host-owned and generic. Before the release, Opening View framing changes from renderer-specific `zoom` to Ground Span, defined as the number of Ground Plane units framed across the viewport height.

`@under-glass/core` also gains a separately versioned Asset Definition v1 JSON contract and generated JSON Schema. An Asset Definition is self-describing and contains:

- its Asset ID;
- one positive uniform scale;
- an arbitrary normalized quaternion used only to correct the authored GLB orientation;
- a Ground Contact point in asset-local X/Y/Z coordinates;
- one rectangular Asset Footprint in asset-local X/Z coordinates;
- required Asset Provenance with a license identifier and source, plus optional author and copyright;
- optional named Connection Ports with asset-local positions and outward Ground Plane normals, retained for `v0.2` but not rendered in this release.

The Asset Definition does not contain a URL or binary data. The host Asset Resolver returns the definition and GLB bytes as an `ArrayBuffer`, keeping storage, authentication, CORS, retries, and cache policy outside the renderer. The repository may provide a small URL resolver helper without adding a second renderer loading contract.

## Scene behaviour

- Only self-contained, uncompressed GLB assets are supported. Multi-file glTF, Draco, Meshopt, KTX2/Basis, and other decoder delivery are deferred.
- GLB animation clips remain stopped at the deterministic rest pose. Embedded cameras and lights are ignored.
- The same Asset ID resolves and parses once per renderer lifecycle even when used by multiple Nodes.
- Ground Plane presentation bounds are derived from the union of Group Bounds and placed Asset Footprints plus theme padding.
- Groups render as flat tinted regions with a subtle border and do not change member Node elevation.
- Node and optional Group labels use an HTML overlay projected from scene anchors. Basic labels do not yet avoid collisions or change visibility with zoom.
- The single Default Scene Theme preserves authored PBR materials and supplies deterministic color management, studio lighting, anti-aliasing, and soft cast/contact shadows. Custom theme configuration, post-processing, outlines, hover, selection, and decorative motion are deferred.
- Isometric mode uses a canonical orthographic camera with a 45-degree yaw and approximately 35.264-degree pitch. Top mode is perpendicular to the Ground Plane. Switching modes preserves center, quarter-turn orientation, and Ground Span.
- The playground exposes only the isometric/top verification toggle. Visitor pan, zoom, scene rotation controls, and React component APIs are not part of this release.

## Lifecycle and diagnostics

The renderer exposes `loading`, `ready`, and `failed` states with structured diagnostics carrying a stable code, severity, related entity ID when available, and human-readable message.

Ground Plane, Groups, labels, and Asset Placeholders appear without waiting for every GLB. Each successfully parsed asset independently replaces its Placeholder. The scene becomes `ready` after every asset has either loaded or produced a recoverable diagnostic; `ready` may therefore include Placeholders and diagnostics.

Fatal structural or semantic validation failures, a missing WebGL2 context, and a Visualization with non-empty Connections leave the renderer `failed`. Connections are deliberately deferred to `v0.2` and are never silently omitted from an apparently complete scene. A Node outside its saved Group Bounds is rendered without repair and produces a diagnostic; the renderer never moves the Node or expands the Group.

The playground shows a compact diagnostics panel. It also renders a static semantic summary from a host-supplied accessible label and the Visualization's Nodes and Groups. Focus synchronization, spatial keyboard navigation, selection, and authoring accessibility belong to later Viewer and Editor milestones.

## Canonical evidence

The checked-in fixture contains 12 Nodes, two Groups, repeated uses of one neutral repository-owned GLB at different quarter-turns, one unresolved Asset ID, no Connections, and a saved Opening View. The GLB carries explicit provenance and is not part of the later starter pack.

Release gates are:

- required GitHub Actions project-check, Fallow, and browser checks on every pull request into `development`;
- structural, semantic, lifecycle, camera, placement, and diagnostic tests;
- deterministic Playwright screenshots for isometric mode, top mode, and the Asset Placeholder state in pinned Chromium;
- explicit screenshot review for intentional visual changes;
- a non-gating 200-Node stress fixture that exposes crashes, leaks, repeated asset parsing, and obvious architectural performance problems before the `v1.0` performance commitment;
- renderer teardown tests demonstrating that recreated scenes release DOM listeners and GPU resources;
- a graceful `renderer-unavailable` state with semantic content when WebGL2 cannot start;
- a publicly accessible static playground preview;
- lockstep `0.1.0` manifests, release notes, and a GitHub `v0.1.0` tag/release.

## Explicitly deferred

- Connection rendering, routing, lanes, crossings, Route Anchors, and Route Conflicts;
- starter asset models;
- live Visualization reconciliation;
- framework-neutral ViewerController and public React adapters;
- pan, zoom, scene rotation, pointer selection, and keyboard interaction;
- automatic Asset Definition derivation or calibration UI;
- custom Scene Themes;
- PNG export and Poster generation;
- npm publication and compatibility promises beyond the pinned Chromium release baseline.
